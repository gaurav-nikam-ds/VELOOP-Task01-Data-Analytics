06 · Wallet & withdrawals

Wallet & withdrawal analytics

Treat wallet movements as a ledger, not a mutable balance-only table. Preserve the complete request and payout state history.

Wallet ledger equation

Opening balance + credits − debits ± adjustments = closing balance

Reconcile by user, unit, ledger period and transaction reference. Reversals must be linked and opposite to the original amount where applicable.

07 · Referral & engagement

Referral & engagement analytics

Define referral eligibility and activation policy before attribution or reward metrics are published.

Referral conversion funnel

CreatedInvite generated
RegisteredNew account
ActivatedApproved qualifying action
EligiblePolicy conditions met
RewardedLedger transaction posted

Feature engagement

Feature adoption = distinct eligible users with a qualifying feature event / eligible active users. Specify eligible audience, event semantics and observation period.

Report active users, returning users, frequency, feature adoption and task completion by cohort. Avoid equating raw event volume with engagement quality.

Attribution policy is a business decision. Proposed analytical convention: one eligible canonical referral per referred user, with self-referrals invalid and subsequent records retained for audit. This requires Product/Growth/Legal approval before production use.

Relationship intent: one user can have many task attempts, rewards, wallet transactions, withdrawals, feature events and product events. Referral records connect a referrer user to a referred user. Reward and wallet references must be traceable and typed; a polymorphic reference requires explicit validation rules.

Modeling rules

  • Use stable surrogate primary keys and explicit foreign keys.
  • Keep transaction/event facts append-only; represent corrections as linked entries.
  • Store event occurrence and ingestion timestamps separately.
  • Declare reward/wallet units and decimal precision.
  • Preserve state history for tasks, rewards and withdrawals.
  • Document polymorphic references and reconciliation constraints.

17 · Privacy and control

Privacy & data governance proposal

Least privilege, data minimisation, controlled retention and documented accountability.

Access model

  • Role-based access for Product, Analytics, Engineering, Finance and Support.
  • Restrict direct identifiers and payout details to approved roles.
  • Use pseudonymous user keys in analytics views.
  • Log privileged access and sensitive exports.

Data lifecycle

  • Collect only fields required for a documented purpose.
  • Define retention and deletion schedules with Legal/Security.
  • Encrypt data in transit and at rest.
  • Keep secrets out of source code and browser bundles.

Quality ownership

  • Product owns event meaning and eligibility.
  • Engineering owns instrumentation and source reliability.
  • Finance/Operations own ledger and payout definitions.
  • Analytics owns metric implementation and monitoring.

Change control

  • Version event schemas and KPI definitions.
  • Record owner, rationale, impact and effective date.
  • Backfill or dual-run breaking changes where appropriate.
  • Require approval before metric definition changes.
This is a proposed control framework, not a legal compliance certification. Security and Legal must review the actual processing purpose, jurisdiction, lawful basis, retention and vendor controls.
